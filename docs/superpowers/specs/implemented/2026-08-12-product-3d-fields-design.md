# 3D-поля товару: model3dPath + texture3dUrl (контракт БД ↔ API ↔ магазин)

**Дата:** 2026-08-12
**Гілка:** `v2` (фронт); зміни схеми — в окремому бекенд-репозиторії
**Статус:** спека затверджена користувачем («додай це в спеку»)

---

## Задача

Товар у базі має знати свою 3D-подачу: **яка геометрія** (крій) і **яка
текстура дизайну** на неї натягується. Магазин підставляє текстуру конкретного
товару в готову сцену (`TshirtScene mapUrl` — API під це вже збудований і
перевірений перемикачем дизайнів у герої).

Підтверджений факт: фото товарів уже зберігаються як Cloudinary URL + publicId
(`ProductImage`), файли — в CDN. 3D-поля повторюють цей патерн.

## Поля на об'єкті Product

| Поле                | Тип            | Що зберігає                                                       |
| ------------------- | -------------- | ----------------------------------------------------------------- |
| `model3dPath`       | string \| null | Шлях/URL геометрії крою, напр. `/3d/models/tshirt.glb`            |
| `texture3dUrl`      | string \| null | Cloudinary URL запеченої basecolor-текстури дизайну (2048², JPEG) |
| `texture3dPublicId` | string \| null | Cloudinary publicId — для керування файлом з адмінки (як у фото)  |

- Обидва `null` = товар без 3D (магазин показує звичайні фото — нічого не
  ламається).
- `texture3dUrl` без `model3dPath` — невалідний стан (текстурі нема на що
  лягати); валідується на бекенді.

### Чому модель — «path», а текстура — «url» (різна природа)

- **Геометрія (GLB)** — це «двигун»: один файл на КРІЙ (не на товар!),
  великий (~1.3 МБ), версіонується разом із кодом сцени (шейдери вітру/маси
  калібровані під конкретну модель). Живе у фронтенд-репо
  `public/3d/models/`, деплоїться з сайтом, кешується назавжди. У базі — лише
  рядок-шлях, який фронт трактує як непрозорий URL. 50 футболок одного крою =
  однакове `model3dPath` у всіх.
- **Текстура дизайну** — це «контент»: своя на товар, легка (~60–100 КБ),
  завантажується менеджером через адмінку без релізу коду. Живе в Cloudinary,
  як усі картинки товарів. Дизайнер може вантажити оригінал 7936² PNG —
  магазин тягне трансформований варіант (`w_2048,q_auto` в URL): серверний
  ресайз безкоштовний, наш ручний sharp-крок зникає.

Одна текстура на товар (basecolor). Normal map (фактура тканини) спільна для
крою і запечена в GLB — окремого поля не потребує.

## Бекенд (окремий репозиторій)

- Міграція Prisma: три nullable-колонки на `Product` (див. таблицю).
- Product-ендпоінти (і каталог, і сторінка товару) віддають нові поля.
- Завантаження текстури: тим самим механізмом, що фото
  (`/admin/products/:id/images` як зразок) — окремий ендпоінт або параметр
  `kind=texture3d`; файл у Cloudinary, `url`+`publicId` у колонки.
- Валідація: квадратна картинка ≥2048, JPEG/PNG; `texture3dUrl` лише разом
  із `model3dPath`.

## Адмінка (цей репо, `/admin`)

- У формі товару: селект «3D-модель» (список відомих кроїв; поки один —
  «Футболка T28» → `/3d/models/tshirt.glb`) + поле завантаження «3D-текстура»
  (переюз наявного компонента завантаження фото).
- Дисципліна (не перевіряється кодом): текстура мусить бути запечена під UV
  саме обраного крою, інакше принт з'їде. Пам'ятка — прямо в UI поля.

## Магазин (цей репо)

- Сторінка товару: якщо в товару є обидва поля — блок 3D-в'юера
  (`TshirtScene` з `mapUrl={texture3dUrl}` і моделлю з `model3dPath`;
  сцена вже параметризована, потрібен лише UI-блок).
- Герой: `DESIGNS`-конфіг згодом наповнюється з API (наприклад, featured-
  товари з 3D) замість хардкоду. Окремий крок, не блокує базу.
- `TshirtScene` отримає проп `modelUrl` (зараз константа) — дрібна зміна,
  готує ґрунт під другий крій (худі).

## Крайові випадки

| Випадок                        | Поведінка                                                                         |
| ------------------------------ | --------------------------------------------------------------------------------- |
| Товар без 3D-полів             | сторінка товару як зараз (фото), без в'юера                                       |
| Текстура є, модель null        | бекенд не дає зберегти (валідація)                                                |
| Битий/недоступний texture3dUrl | в'юер лишає запечений дефолт мапи + console.warn (наявна поведінка useDesignMap)  |
| Новий крій (худі)              | новий GLB у `public/3d/models/` + пункт у селекті адмінки; схема БД не змінюється |

## Свідомо не робимо (YAGNI)

Бінарники в Postgres (повільно/дорого/без плюсів проти CDN), кілька текстур
на товар, per-variant текстури (розмір не міняє принт), автоматичні
Blender-рендери фолбеків (фолбек = наявні фото товару), зберігання GLB у
Cloudinary (можливо колись для кроїв поза релізним циклом — не зараз).

## Порядок впровадження

1. Бекенд: міграція + віддача полів + upload (робиться в бекенд-репо).
2. Адмінка: два поля у формі товару.
3. Магазин: в'юер на сторінці товару → потім герой з API.

Фронтова 3D-механіка (сцена, вітер, маса, драг, свопи текстур) готова і не
змінюється — це суто задача даних і двох шматків UI.
