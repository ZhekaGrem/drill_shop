# v2 Visual Bug Audit — Design

**Date:** 2026-08-10
**Branch:** v2

## Проблема

На гілці `v2` (редизайн у стилі Дії) під час ручного перегляду виявлено візуальні/верстальні
баги — на мобільному і на десктопному екрані. Найбільше на сторінці товару, менше в каталозі,
є баги в чекауті. Потрібен систематичний прохід по цих сторінках через chrome-devtools MCP,
фіксація всіх знайдених дефектів у список, узгодження зі мною, і потім виправлення.

## Обсяг

**Маршрути:**
- `/catalog` (каталог)
- `/catalog/[slug]` (сторінка товару, реальний товар з seed-даних бекенду)
- `/cart` → `/checkout` (товар у кошик додається вручну через UI під час аудиту)

**Viewport-и (кожна сторінка в обох):**
- Мобільний: 375×812
- Десктоп: 1440×900

**Тип дефектів:** тільки візуальні/верстальні — переповнення (overflow), накладання елементів,
зламаний grid/flex, обрізаний текст, неправильні відступи, зламана адаптивність.
Функціональні баги (кнопки не працюють, неправильна логіка) — поза обсягом.

**Поза обсягом:** інші сторінки (about, profile, admin тощо), бекендна логіка, non-visual баги.

## Тестове середовище

Дані мають бути реальними, не заглушками — довгі назви товарів, реальні пропорції фото з
Cloudinary, реальна кількість варіантів/розмірів і реальні ціни є типовими тригерами саме тих
багів, які шукаємо. Заглушки з коротким текстом і плейсхолдер-картинкою це б приховали.

1. Підняти бекенд локально: `F:\Progect\2025\shop_bogdan\backend` → `npm run dev`
   (`.env` вже налаштований, є реальне підключення до БД)
2. Якщо БД порожня — `npm run db:seed` у бекенді
3. Підняти фронтенд v2 локально: `npm run dev` у цьому репо (порт 3000)
4. Перевірити, що `NEXT_PUBLIC_API_URL=http://localhost:3001/api/v1` збігається з портом бекенду
5. chrome-devtools MCP підключається до `http://localhost:3000`

## Методологія аудиту

Для кожної пари (сторінка × viewport):
1. Відкрити сторінку в chrome-devtools MCP з відповідним viewport
2. Зробити скріншот
3. Там, де скріншот показує аномалію — інспектувати DOM / computed styles відповідного
   елемента, щоб знайти причину (переповнення, конфлікт flex/grid, хардкод розміру, відсутній
   media query тощо)
4. Записати знахідку: сторінка, viewport, компонент/файл (якщо визначено), опис бага,
   ймовірна причина

Для чекауту: додати товар у кошик через реальний UI-флоу (каталог → товар → "у кошик" →
кошик → чекаут), а не напряму через API — це також перевіряє сам флоу переходу.

## Результат аудиту

Після проходу всіх сторінок × viewport-ів — показати користувачу зведений список усіх
знайдених дефектів (без виправлень). Чекати підтвердження, перш ніж починати фікси.

## Виправлення

- Точкові правки, без рефакторингу поза межами знайдених багів
- Дотримання правила "Єдиного Джерела" стилізації з CLAUDE.md: Mantine props АБО SCSS module
  АБО inline styles для одного елемента — без міксування
- Кольори/розміри/spacing — тільки токени з `src/app/globals.css` (`:root`), без хардкоду hex
  чи "магічних" px
- Не чіпати FSD-межі (`shared` не імпортує з `features`, без cross-feature імпортів)

## Верифікація фіксу

Для кожного виправленого бага:
1. Повторний скріншот того самого місця (той самий viewport) — підтвердити, що дефект зник
2. Перевірити, що інші елементи поруч не зламались (той самий скріншот)
3. Після всіх фіксів — `npm run lint` має бути чистим

## Помилки/ризики

- Порт бекенду може не збігатись з `NEXT_PUBLIC_API_URL` — перевірити на старті, за потреби
  скоригувати `.env.local` або порт бекенду
- Якщо в БД немає товарів — потрібен `db:seed` перед аудитом каталогу/товару/кошика
- chrome-devtools MCP сервер зараз ще підключається (побачено на старті сесії) — перевірити
  доступність перед стартом аудиту
