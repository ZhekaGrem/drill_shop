## 0. TL;DR

Товар отримує три nullable-поля: `model3dPath` (який крій-GLB),
`texture3dUrl` + `texture3dPublicId` (Cloudinary-текстура дизайну).
Бекенд — міграція + віддача полів + upload/delete ендпоінт текстури.
Адмінка — селект крою + завантаження текстури у формі товару.
Магазин — 3D-в'юер на сторінці товару, який підставляє текстуру товару в уже
готову сцену `TshirtScene` через наявний проп `mapUrl`.
Фронтовий 3D-двигун (вітер, маса, драг, своп текстур) готовий і не змінюється.

- `public/3d/textures/tshirt-no-{red,violet,green,yellow,runic,white-violet}.jpg`

### 1.3 Патерн зберігання картинок (підтверджено кодом)

`ProductImage` (`src/shared/types/generated.types.ts:210`): у БД лише

## 2. Глосарій

- **Крій (cut)** — геометрія одягу: файл GLB. Один файл обслуговує всі товари
  цього крою. Зараз крій один: футболка T28 Oversized.
- **Текстура дизайну (basecolor)** — квадратна картинка, запечена під
  UV-розгортку конкретного крою; несе принт + колір тканини. Своя на товар.
- **Normal map** — фактура тканини (шви, складки). Спільна для крою,
  запечена всередині GLB. Окремого поля в БД не потребує.
- **UV-розгортка** — відповідність «точка на картинці → точка на 3D-моделі».
  Текстура, запечена під інший крій, дає з'їханий принт — це дисципліна
  дизайнера, кодом не перевіряється.

## 3. Цільова архітектура

```
дизайнер            адмінка                Cloudinary              PostgreSQL
готує PNG ──────▶ форма товару ──────▶ upload (оригінал) ──▶ url + publicId
за UV-шаблоном    (multipart file)          │                 на Product
крою                                        │
                                            ▼
магазин ◀──────────────────────────  w_2048,q_auto
сторінка товару: TshirtScene         (трансформація на льоту,
mapUrl = texture3dUrl(2048)           без ручної конвертації)
modelUrl = model3dPath ────────────▶ /3d/models/*.glb (статика цього репо)
```

### 3.1 Модель даних — три поля на `Product`

| Поле                | Тип              | Семантика                                                                 |
| ------------------- | ---------------- | ------------------------------------------------------------------------- |
| `model3dPath`       | `string \| null` | Шлях геометрії крою, напр. `/3d/models/tshirt.glb`. Фронт трактує як непрозорий URL |
| `texture3dUrl`      | `string \| null` | Canonical Cloudinary secure_url оригіналу текстури                        |
| `texture3dPublicId` | `string \| null` | Cloudinary publicId — для трансформацій на фронті та видалення з адмінки  |

Інваріанти:

- Обидві «половини» відсутні → товар без 3D, усе працює як зараз.
- `texture3dUrl` без `model3dPath` — невалідний стан, бекенд відхиляє.
- `model3dPath` без текстури — валідний (в'юер покаже запечений у GLB
  дефолтний дизайн); але UI магазину показує в'юер лише коли є ОБИДВА поля
  (див. C4) — щоб чужий дефолтний принт не видавався за принт товару.
- Чому модель — «path», а текстура — «url»: GLB один на крій, важкий,
  калібрований із шейдерами → живе в репо і їде з релізом; текстура — контент
  на товар, легка → їде через адмінку без релізу.

## 4. ЧАСТИНА A — Бекенд (окремий репозиторій)

> Репозиторій бекенду недоступний з місця написання цього ТЗ. Контракти
> (маршрути, JSON, коди помилок) — нормативні; назви файлів/хелперів усередині
> бекенду — орієнтовні, слідувати наявним конвенціям того репо (насамперед
> реалізації `uploadImages`).

### A1. Схема Prisma + міграція

```prisma
model Product {
  // ... наявні поля без змін ...
  model3dPath       String? @map("model_3d_path")
  texture3dUrl      String? @map("texture_3d_url")
  texture3dPublicId String? @map("texture_3d_public_id")
}
```

Еквівалент SQL (назву таблиці та конвенцію `@map` звірити з наявною схемою —
якщо проєкт не використовує `@map`, лишити camelCase як усюди):

```sql
ALTER TABLE "products"
  ADD COLUMN "model_3d_path"        TEXT,
  ADD COLUMN "texture_3d_url"       TEXT,
  ADD COLUMN "texture_3d_public_id" TEXT;
```

Міграція чиста адитивна: без backfill, без зміни наявних рядків, без
downtime-ризиків.

### A2. Віддача полів (read-контракт)

Три поля додаються в серіалізацію товару всюди, де віддається Product:

| Ендпоінт                         | Використання на фронті                  |
| -------------------------------- | ---------------------------------------- |
| `GET /products/:slug`            | сторінка товару (SSG) — головний споживач |
| `GET /products`, `/products/featured`, `/products/popular` | каталог, герой (фаза 2) |
| `GET /admin/products/:id`        | форма адмінки                            |

Приклад фрагмента відповіді (обгортка — та сама, що в наявних
product-відповідях):

```json
{
  "success": true,
  "data": {
    "id": "cku…",
    "slug": "no-red-tee",
    "name": "Футболка NO червона",
    "model3dPath": "/3d/models/tshirt.glb",
    "texture3dUrl": "https://res.cloudinary.com/<cloud>/image/upload/v1723456789/products/3d-textures/abc123.jpg",
    "texture3dPublicId": "products/3d-textures/abc123"
  }
}
```

Товар без 3D віддає `"model3dPath": null` тощо (або поля відсутні — фронт
готовий до обох варіантів, бо типи optional-nullable).

### A3. Запис `model3dPath`

Через наявний `PATCH /admin/products/:id` (`adminEndpoints.products.update`):
додати `model3dPath` у whitelist полів апдейту. Значення — довільний рядок
або `null`; бекенд НЕ валідує його проти списку кроїв (список живе у фронті,
див. B1) — лише обрізає пробіли і обмежує довжину (напр. 512).

Правило узгодженості: якщо запит виставляє `model3dPath = null`, а в товару є
текстура — відповісти `400 TEXTURE_REQUIRES_MODEL` (або в одній транзакції
чистити й текстурні поля + Cloudinary-файл; обрати перше — простіше і
безпечніше, видалення текстури хай буде явним через A5).

### A4. Завантаження текстури

```
POST /admin/products/:id/texture3d
Content-Type: multipart/form-data
Поле файла: "file" (одна картинка)
Ролі: ті самі, що на uploadImages (admin/manager)
```

Кроки сервера:

1. Товар існує, інакше 404. `model3dPath` заповнений, інакше
   `400 TEXTURE_REQUIRES_MODEL`.
2. MIME whitelist: `image/jpeg`, `image/png`, `image/webp`. Ліміт розміру
   файла — 10 МБ (стеля image-upload на free-плані Cloudinary; звірити з
   фактичним планом і лімітом multer у наявному upload).
3. Завантаження в Cloudinary **без eager-трансформацій** (магазин трансформує
   на льоту):

   ```js
   const result = await cloudinary.uploader.upload(tmpPath, {
     folder: 'products/3d-textures',
     resource_type: 'image',
   });
   ```

4. Валідація геометрії картинки — з метаданих відповіді Cloudinary (локальна
   image-бібліотека не потрібна):

   ```js
   if (result.width !== result.height || result.width < 2048) {
     await cloudinary.uploader.destroy(result.public_id);
     return res.status(400).json({ success: false, error: 'TEXTURE_INVALID_DIMENSIONS' });
   }
   ```

5. Оновити товар: `texture3dUrl = result.secure_url`,
   `texture3dPublicId = result.public_id`.
6. Якщо в товару БУЛА текстура з іншим `publicId` — після успішного запису в
   БД викликати `cloudinary.uploader.destroy(старий publicId)`. Помилку
   destroy лише логувати (орфан у Cloudinary прийнятний, битий стан у БД — ні).
7. Відповідь:

   ```json
   {
     "success": true,
     "data": {
       "texture3dUrl": "https://res.cloudinary.com/…/products/3d-textures/abc123.jpg",
       "texture3dPublicId": "products/3d-textures/abc123"
     }
   }
   ```

### A5. Видалення текстури

```
DELETE /admin/products/:id/texture3d
```

Обнуляє `texture3dUrl` + `texture3dPublicId` у БД, потім destroy у Cloudinary
(той самий принцип: БД — джерело правди, destroy-помилка лише в лог).
`model3dPath` НЕ чіпає. Відповідь `{ "success": true }`.

При видаленні самого товару — включити texture3dPublicId у ту саму процедуру
очищення Cloudinary, яка діє для ProductImage (якщо така є; якщо ні — не
вигадувати нову, лишити симетрично з картинками).

### A6. Коди помилок (нормативні)

| HTTP | Код                          | Коли                                            |
| ---- | ---------------------------- | ----------------------------------------------- |
| 400  | `TEXTURE_REQUIRES_MODEL`     | аплоад/збереження текстури при `model3dPath = null` |
| 400  | `TEXTURE_INVALID_DIMENSIONS` | не квадратна або < 2048px                       |
| 400  | `TEXTURE_INVALID_FORMAT`     | MIME поза whitelist                             |
| 413  | —                            | файл понад ліміт                                |
| 404  | —                            | товару не існує                                 |

### A7. Приймальні критерії (бекенд)

- [ ] Міграція накочується і відкочується без втрати наявних даних.
- [ ] `GET /products/:slug` віддає три поля; для товару без 3D — null/відсутні.
- [ ] `PATCH /admin/products/:id` приймає та очищає `model3dPath`; спроба
      зняти модель при живій текстурі → `400 TEXTURE_REQUIRES_MODEL`.
- [ ] POST texture3d: happy path записує url+publicId; повторний аплоад
      підміняє файл і destroy'їть старий; невалідні розміри/формат/розмір
      файла → відповідні 400/413; без `model3dPath` → 400.
- [ ] DELETE texture3d чистить поля і файл.
- [ ] Ендпоінти захищені тими самими ролями, що й uploadImages.

- **Селект «3D-модель (крій)»** — options з `MODELS_3D`

- **Завантаження текстури** — `FileInput` (accept `image/jpeg,image/png,image/webp`).

  3D-модель»).
- **Прев'ю поточної текстури** — якщо `product.texture3dPublicId` є:
  `getCloudinaryUrl(product.texture3dPublicId, { width: 256, crop: 'limit' })`

- **Пам'ятка в UI** (Text size="xs" c="dimmed"): «Квадрат ≥2048px, JPEG/PNG,

  інакше принт з'їде.»
- **Попередження при зміні крою з живою текстурою**: якщо користувач міняє
  селект, а `texture3dUrl` заповнений — показати warning-текст «Поточна

- **Доступність секції**: лише для збереженого товару (є `product.id`).
  У режимі створення — placeholder «Збережіть товар, щоб додати 3D».

Підключення: у `ProductForm.tsx` поруч із `ProductImageManager`.

## 6. ЧАСТИНА C — Магазин (цей репозиторій)

### C1. Дрібні розширення двигуна (2 файли)

**`TshirtScene.tsx`** — модель пропом замість константи:

- `MODEL_URL` → `DEFAULT_MODEL_URL` (те саме значення `'/3d/models/tshirt.glb'`);
  `useGLTF.preload(DEFAULT_MODEL_URL)` лишається (герой).
- Props: `modelUrl?: string` (дефолт `DEFAULT_MODEL_URL`) і
  `onMapReady?: () => void` (прокидається в `useDesignMap`).
- `useGLTF(MODEL_URL)` → `useGLTF(modelUrl)` (і в `Tshirt`, і прокинути з
  обгортки `TshirtScene`).
- Увага: файл зараз рівно 150/150 рядків (ліміт CLAUDE.md). Дві нові
  props-стрічки компенсувати ущільненням сусідніх коментарів — ліміт не
  перевищувати.

Сцена вже модель-агностична: висота стрибка і pivot міряються Box3, вітер
міряє bounding box геометрії, камеру підганяє `<Bounds>`. Новий крій пройде
без змін коду, але з обов'язковою візуальною перевіркою калібрувань (див. §7.2).

**`useDesignMap.ts`** — сигнал «мапа застосована»:

```ts
export const useDesignMap = (scene: Group, mapUrl?: string, onApplied?: () => void) => {
```

`onApplied?.()` викликається в трьох місцях одразу після присвоєння
`material.map`: гілка `!mapUrl` (повернення оригіналу), гілка кешу, колбек
успішного завантаження (всередині guard `wanted.current === mapUrl`). При
помилці завантаження НЕ викликається (в'юер лишиться на фолбеку-фото — див.
C3; для героя поведінка без змін, він проп не передає).

### C2. URL текстури для сцени

Правило: **якщо є `texture3dPublicId` — будувати URL трансформації через
наявний хелпер; сирий `texture3dUrl` — запасний варіант** (оригінал може бути
7936² і важити мегабайти):

```ts
import { getCloudinaryUrl } from '@/shared/utils/cloudinary';

const textureUrl = product.texture3dPublicId
  ? getCloudinaryUrl(product.texture3dPublicId, { width: 2048, crop: 'limit', quality: 'auto' })
  : (product.texture3dUrl ?? undefined);
```

- `c_limit` не апскейлить менші оригінали.
- `f_auto` (дефолт хелпера) віддасть webp/avif — `TextureLoader` вантажить
  через `HTMLImageElement`, сучасні браузери декодують обидва. Якщо на
  тестах C6 виявиться проблемний декод — зафіксувати `format: 'jpg'`.
- CORS: three.js вантажить з `crossOrigin='anonymous'`; `res.cloudinary.com`
  віддає `Access-Control-Allow-Origin: *` — перевірити один раз на
  реальному URL (інакше WebGL відхилить текстуру як tainted).

### C3. Новий віджет `src/widgets/Product3DViewer/`

```
Product3DViewer/
├── Product3DViewer.tsx          // ліміт 150 рядків
├── Product3DViewer.module.scss
└── index.ts
```

Проп: `{ product: Product }`. Поведінка — зменшена копія перевірених рішень
`HeroVisual.tsx` (брати патерни звідти, спільний код НЕ витягувати передчасно):

1. **Гейт даних**: рендериться тільки якщо `model3dPath` І текстурний URL
   (C2) обидва є. Інакше — `return null` (сторінка товару як зараз).
2. **Lazy-завантаження**: сцена (`lazy(() => import('@/widgets/HeroVisual/TshirtScene'))`)
   монтується після появи блока у в'юпорті (IntersectionObserver, як у
   HeroVisual) — three.js не вантажиться, поки користувач не доскролив.
3. **Фолбек до готовності**: фото товару (`product.primaryImage?.url` через
   `next/image`) видиме, поки сцена не готова.
4. **Reveal-гейт**: канвас проявляється (fade, як `.scene/.sceneReady` у
   `HeroVisual.module.scss`) лише після `onReady` **і** `onMapReady` — інакше
   користувач на мить побачить запечений у GLB чужий дизайн (червоний) на
   сторінці, скажімо, зеленої футболки. Це головна відмінність від героя.
5. **Помилки**: будь-який фейл (текстура не завантажилась → onMapReady не
   прийшов; WebGL недоступний; GLB 404) = канвас просто не проявляється, фото
   лишається. Обгорнути сцену в наявний Error Boundary
   (`src/shared/providers/`) — краш R3F не має валити сторінку.
6. **Драг**: `useDragRotation` + `dragRef` + `touch-action: pan-y` +
   курсори grab/grabbing — усе як у героя. `interactive` (стрибок) не
   вмикати (YAGNI, проп існує на майбутнє).
7. **Розміри**: квадратний блок `aspect-ratio: 1`, `max-width` за макетом
   галереї; на мобілці — повна ширина картки. Точна висота — за наявною
   сіткою `ProductDetailsClient`, не вигадувати нову.

### C4. Інтеграція в сторінку товару

`src/app/catalog/[slug]/ProductDetailsClient.tsx`: відрендерити
`<Product3DViewer product={product} />` у зоні галереї (під/поруч із фото —
за макетом). Шар FSD чистий: app → widgets дозволено. Дані вже на місці —
компонент отримує той самий `initialProduct`, який після A2 нестиме 3D-поля.

Нюанс ISR: сторінка товару — SSG з `revalidate = 86400`. Після зміни текстури
в адмінці магазин побачить її після ревалідації (до 24 год) або редеплою.
Якщо знадобиться миттєво — окрема задача про on-demand revalidation, у це ТЗ
не входить.

### C5. Фаза 2 (окремий крок, не блокує): герой з API

`DESIGNS` героя (зараз хардкод у `HeroVisual.tsx`) наповнюється з
`productEndpoints.featured`: товари з обома 3D-полями → `{ label: name,
fallback: primaryImage.url, mapUrl: C2-URL }`. Відкрите питання, яке треба
вирішити перед цією фазою: колір крапки-свотча в БД відсутній (зараз хардкод
hex). Варіанти: похідне поле `swatchColor` на товарі або відмова від
кольорових крапок на користь міні-прев'ю. Не проєктувати зараз.

### C6. Приймальні критерії (магазин)

- [ ] Товар з 3D: фото → плавний перехід у 3D вже з ПРАВИЛЬНОЮ текстурою
      (жодного кадру червоного дефолту), вітер + інерція + драг працюють.
- [ ] Товар без 3D: сторінка байт-у-байт як зараз (жодного канвасу/чанку three).
- [ ] Битий texture3dUrl (підмінити руками): канвас не проявляється, фото
      стоїть, у консолі один warn.
- [ ] Мобілка (реальний iPhone): драг крутить, вертикальний скрол сторінки
      живий (`pan-y`), світчер/кнопки сторінки клікабельні.
- [ ] Повільна мережа (throttle Fast 3G): фолбек-фото видиме одразу, LCP не
      деградує (three-чанк вантажиться після в'юпорт-гейта).
- [ ] `npm run build` зелений; сторінки без 3D не тягнуть three у бандл
      (перевірити аналізом чанків або network-табом).

## 7. Інваріанти 3D — обов'язкові для всіх частин

### 7.1 Вимоги до текстури дизайну

| Параметр      | Вимога                                                                  |
| ------------- | ----------------------------------------------------------------------- |
| Геометрія     | квадрат, ≥2048px (бекенд ріже менше/неквадратне — A4)                    |
| Формат        | JPEG / PNG / WebP, ≤10 МБ                                                |
| Вміст         | запечена під UV-розгортку САМЕ обраного крою; sRGB; альфа не використовується |
| Орієнтація    | стандарт glTF: `flipY=false` виставляє рантайм (`useDesignMap`), файл звичайний |
| Рекомендація  | експорт 4096² JPEG q90 (~3–6 МБ): якість із запасом, влазить у ліміт     |

### 7.2 Вимоги до GLB нового крою (коли з'явиться)

- Одна меш з `MeshStandardMaterial` (`map` = запечений дефолтний дизайн +
  `normalMap`); перед моделі дивиться в **+Z**; реальний масштаб (~0.7 м
  висоти для футболки).
- Стиснення: KHR_mesh_quantization + EXT_meshopt_compression (декодер уже
  підключений через drei `useGLTF`). Бюджет файла ≤1.5 МБ.
- **Ніколи не редагувати BIN-чанк вручну** — тільки конвеєр
  `@gltf-transform` (див. додаток 12.2).
- Подвійношарова тканина (внутрішній+зовнішній шар на відстані <1 мм):
  допустима — вітер зсуває вершини радіально, а не вздовж нормалей, шари не
  перетинаються. Але після додавання крою обов'язковий візуальний прогін:
  вітер, драг, стрибок (`interactive=true` тимчасово), обидві теми, мобілка.
- Реєстрація: файл у `public/3d/models/`, запис у `MODELS_3D` (B1). Схема БД
  не змінюється.

### 7.3 Кешування і мережа

- Cloudinary-URL версіоновані (`/v1723…/`) — кешуються назавжди, підміна
  текстури = новий URL, стейл-кешу не буває.
- `useDesignMap` кешує `Texture` по URL у пам'яті — повторний показ миттєвий.
- GLB з `public/` їде зі статикою Vercel; узгоджувати додатково нічого не
  треба (same-origin).

### 7.4 Бюджети продуктивності

- Один `<Canvas>` на сторінку. Сторінка товару: в'юер + жодних інших сцен.
- Текстура в рантаймі: 2048², ~60–300 КБ по мережі (q_auto).
- `dpr={[1, 2]}`, `antialias: true` — як у героя, не чіпати.

## 12. Додатки

### 12.1 SOP дизайнеру: підготовка текстури

1. Взяти UV-шаблон крою (розгортка з Blender-проєкту `tshirt 3d/`; для T28 —
   та сама розкладка, під яку запечені поточні `NO *.png`).
2. Розмістити принт/колір по шаблону. Колірний простір sRGB, без альфи.
3. Експорт: квадрат 4096×4096, JPEG quality 90 (~3–6 МБ). PNG допустимий,
   якщо влазить у 10 МБ.
4. Віддати менеджеру → адмінка → перевірити на сторінці товару зі всіх боків
   (драг): принт на спині/грудях на місці, шви не «ріжуть» напис.

### 12.2 SOP розробнику: додавання нового крою

1. З Blender: експорт GLB (одна меш, матеріал із запеченими basecolor 2048 +
   normal map 2048; +Z вперед; реальний масштаб).
2. Оптимізація (ніяких ручних правок бінарника):

   ```bash
   npx @gltf-transform/cli optimize in.glb out.glb \
     --compress meshopt --texture-compress webp --texture-size 2048
   ```

   Ціль ≤1.5 МБ. Якщо basecolor краще тисне JPEG — обробити канали окремо
   скриптом на `@gltf-transform/core`, як зроблено для tshirt.glb
   (basecolor → JPEG, normal map → WebP).
3. Покласти в `public/3d/models/<name>.glb`, додати запис у `MODELS_3D` (B1).
4. Прогін §7.2 (вітер/драг/стрибок/мобілка) + перевірка, що двошаровість
   тканини не дає z-fighting під вітром.
5. Фолбеки для героя (якщо крій піде в герой): Blender-рендер прозорого
   фронтального кадру 1600², для світлої тканини множник світла ~0.42
   (інакше біле вигорає).
